# Бесплатная подпись «Рядом» через SignPath

Подготовлено 15.11.2026 для владельца GitHub
[chico1969](https://github.com/chico1969). Заявка ещё не отправлена, одобрения и
подписанных файлов пока нет. Установленная семейная версия и её настройки не
меняются этой подготовкой.

## Что уже подготовлено

- `CODE_SIGNING.md`: правила подписи, роли, происхождение форка и статус заявки.
- `PRIVACY.md`: сетевые службы и локальные данные, включая ограничения документа.
- `APPLICATION.md`: текст заявки на английском без выдуманной репутации проекта.
- `inner.xml`, `outer.xml`: конфигурации SignPath с точными именами файлов,
  названием продукта и обязательной единой версией.
- `.github/workflows/ryadom-signpath.yml`: ручная Windows-сборка на GitHub,
  два запроса подписи и проверка сертификата. По умолчанию `sign=false`.
- `artifacts.ps1`: проверка метаданных, возвращённых подписей и упаковка уже
  подписанного внутреннего EXE/DLL. После окончательной подписи файлы не меняются.
- `prepare-publication.py`: отдельный архив исходников и Git-патч для публикации
  без изменения рабочего Git-индекса, remotes, установленного приложения или
  текущих EXE. Он проверяет известные локальные TURN-данные, но не заменяет
  проверку всего проекта человеком.

## Что нужно сделать владельцу сейчас

1. В GitHub включить/проверить двухфакторную аутентификацию. Публичный fork
   <https://github.com/chico1969/ryadom> уже создан, исходники опубликованы в
   основной ветке `ryadom`. Повторно создавать или загружать папки не нужно.
2. Проверить опубликованные изменения, безопасность, лицензии и документы.
   Подготовленный Git-патч остаётся локальным средством проверки переноса;
   development release пока не опубликован. Не загружать семейный EXE в публичный
   release: он содержит извлекаемую семейную конфигурацию TURN.
3. После успешной первой GitHub-сборки и закрытия перечисленных ниже условий
   открыть <https://signpath.org/apply>. Взять ответы из `APPLICATION.md`, добавить
   свою контактную почту, фактический download URL и правдивые сведения о проекте.
   Согласие с условиями подтвердить самостоятельно. Пароли, MFA-коды и токены
   не присылать в чат.

**Форк `chico1969/ryadom` и исходники уже опубликованы; CI проверяется отдельно.** Настраивать платный
тариф, покупать сертификат или добавлять карту для этой заявки не требуется.
Официальная программа: <https://signpath.org/>.

## Условия, которые нельзя объявлять выполненными заранее

По <https://signpath.org/terms> проекту нужны публичные исходники, действительный
выпуск, проверяемая репутация, открытые компоненты и проверяемый процесс сборки.
«Рядом» пока новый семейный проект. SignPath вправе отказать; срок и одобрение
не гарантированы. Наличие известного upstream не передаёт форку его репутацию.

До заявки/первой производственной подписи нужно:

- сохранить подтверждение подписанной upstream-сборки: Windows x64 1.5.3 уже
  проверена на этом ПК, подпись PURSLANE действительна, timestamp присутствует;
- завершить проверку лицензий всех реально включённых DLL/компонентов;
- проверить GitHub-сборку на чистых hosted runners: локальная проверка конфигов
  не равна выполненному GitHub workflow;
- проверить применение Git-патча и перенос всех новых исходников в форк;
- включить MFA в GitHub и SignPath, назвать ответственного владельца и контакт;
- в установщике показывать именно политику «Рядом» и дать требуемый программой
  SignPath выбор отключения фонового обмена. Сейчас старый блок установщика
  ссылается на политику RustDesk — документ сам по себе это поведение не меняет;
- опубликовать честно помеченный тестовый выпуск и его исходники, не объявляя
  всю пользовательскую приёмку завершённой.

## После предварительного одобрения SignPath

1. Зарегистрировать/подтвердить аккаунт SignPath, включить MFA. Получить бесплатную
   OSS organization и сначала пройти предложенную SignPath тестовую настройку.
2. Установить официальный SignPath GitHub App с доступом **только к форку**,
   связать trusted build system с проектом `ryadom`.
3. Создать artifact configurations `inner` и `outer` из XML в этой папке.
   Согласовать с проверяющим двухэтапную упаковку и ограничения форка. Создать
   policy `release`, требующую ручного одобрения каждого запроса.
4. В GitHub создать environment `signpath-release`, ограничить разрешённую ветку
   и включить required reviewer. Если доступен один владелец, не включать запрет
   self-review для самого environment; независимое ручное подтверждение в
   SignPath всё равно обязательно. Не выдавать токену право approve.
5. В этом environment задать secret `SIGNPATH_API_TOKEN` (только submitter) и
   variables `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_CERTIFICATE_THUMBPRINT`
   (SHA-1 thumbprint одобренного production-сертификата, без пробелов).
   `RYADOM_SIGNPATH_ENABLED=true` ставится **только после** принятия проекта,
   проверки настроек и прохождения предыдущих условий. Значение не означает
   одобрение само по себе. Токен не входит в EXE или исходники.
6. Запустить workflow с новой четырёхчастной версией, например `0.1.0.1`, сначала
   `sign=false`. После проверки успешной сборки запустить `sign=true`, дождаться
   первого запроса, подтвердить его в SignPath, затем подтвердить второй запрос.
   Отказ, неверный сертификат или отсутствие timestamp останавливают сборку.
7. Проверить подписанные EXE на чистом Windows, затем публиковать вручную вместе
   с соответствующими исходниками и итоговыми SHA256. Workflow сам release не
   публикует. Добавить активное acknowledgement SignPath только после получения
   рабочей production-подписи.

Обычная UAC при установке службы остаётся. Подпись не гарантирует немедленного
исчезновения SmartScreen: <https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation>.

## Публичная и семейная сборки

Публичная CI-сборка намеренно не включает личные ExpressTURN-данные. При сложном
NAT ей потребуется отдельно настроенный TURN; гарантировать такой же резерв,
как у текущего семейного EXE, нельзя. Текущие семейные EXE не заменяются.
Возможность подписывать вариант с семейной конфигурацией нужно отдельно
согласовать с SignPath и владельцем до изменения публичного workflow.
